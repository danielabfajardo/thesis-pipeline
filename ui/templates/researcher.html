1 · SonarQube extraction

Pulls every open issue from the local SonarQube server via /api/issues/search with s=SEVERITY&asc=false so the order matches what a developer sees in SonarQube's UI. SonarQube caps a single filter at 10,000 results — when the project exceeds that, the extractor recursively splits by severity, then type, then rule. File-level quality metrics come from /api/measures/component_tree, fetched in three groups (core / violations / ratings) so one failing group does not block the others. Rule explanations come from /api/rules/show; the AI CodeFix field is dropped.

2 · GitHub churn & blame

Two independent signals. File-level churn (one row per file): commit count, unique authors, bus factor (smallest set of authors covering ≥50% of commits), lines added/deleted, total churn, days since last modified, file age. The window is churn_lookback_days from the project YAML (defaults to 365). Alert-level blame (one row per alert): days since the specific flagged line was last modified, plus author. Computed by paging git blame via the GitHub GraphQL API, then matching each alert's line against the returned ranges. Blame is cached per file, so a file with multiple alerts hits GraphQL once.

3 · SATD detection

Self-admitted technical debt — comments where developers acknowledge known problems. Three paths in fall-through order. Path 1 (SATDBailiff), Java only: a Docker MySQL container plus the SATDBailiff JAR, walks full git history, classifies each comment with Liu et al.'s detector, tracks lifecycle events (added / changed / removed), and returns active at HEAD instances with age and change-count metadata (6-column schema). Path 2 (ML classifier): satd_detector.jar binary classifier; pulls file content from GitHub, extracts comments, batches every comment through the classifier in one subprocess call (3-column schema). Path 3: empty CSV.

4 · 200-alert pool (stratified)

Reduces the full alert set to a balanced 200 the LLM can rank in a single prompt. Tier budgets: HIGH=60, MEDIUM=100, LOW=40. Within each tier, alerts are walked oldest-first by creationDate and picked one by one, skipping any whose rule already has 5 picks in the pool, or whose file already has 3. Both caps are global — counts persist as the loop moves between tiers. Deterministic; no LLM. Justified by Baltes & Ralph (2020): stratified quota sampling for diversity, oldest-first for persistence, rule cap to prevent one noisy rule from dominating.

5 · LLM ranking — C2 (static features only)

Single Anthropic API call. Temperature = 0. The C2 input contains only SonarQube properties and file-level quality metrics — no SonarQube severity, no impact_severity, no impact_quality, no churn, no SATD, no blame. The LLM emits {issue_key, rank, llm_reasoning} per alert. Ranks must be a unique permutation of 1..N; duplicates cause the call to fail loudly. Severity in the UI is always SonarQube's — the LLM never assigns a severity label.

5 · LLM ranking — C3 (static + churn + SATD + blame)

Same prompt structure as C2 but the per-alert JSON adds 11 fields: file_commit_count, file_unique_authors, file_bus_factor, file_churn, file_days_since_modified, file_age_days, file_satd_count, file_satd_text, file_satd_age_days, file_satd_change_count, line_last_modified_days. The C3 prompt cites Nagappan & Ball (2005), Kamei et al. (2013), Yamashita et al. (2015), and Bavota & Russo (2016) for empirical grounding. Same output schema as C2.

6 · 15-alert display set (C1-anchored)

Selects exactly 15 alerts that appear in all three conditions. Same alerts, three orderings. Walks C1 (SonarQube native order) top-to-bottom and picks until the bucket budgets fill: HIGH=5, MEDIUM=7, LOW=3. Max 3 alerts per file. C1-anchoring means the experimental question is "does the LLM re-order what SonarQube considers most important?", not "do the rankings overlap at all?".
