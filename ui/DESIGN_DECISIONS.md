# Interview UI Design Decisions

**Date**: May 9, 2026  
**Context**: Master's thesis study on LLM-based re-prioritization of SonarQube alerts with semi-structured interviews

---

## Critical: SonarQube AI CodeFix Suppression

### Issue
SonarQube 10.x includes AI-generated code fix suggestions in rule explanations via REST API. If participants see AI-generated fixes without knowing they are AI-generated, the interview disclosure ("List 1/2/3 was generated by an LLM") is contaminated.

### Solution
**When displaying rule explanations in the interview UI:**

1. **Check SonarQube configuration**:
   - Query `/api/settings?keys=sonar.ai.codefix.enabled` (or similar)
   - Or query `/api/rules/show` responses for presence of AI suggestions/fixes

2. **If AI CodeFix is enabled**:
   - Option A (Preferred): Disable it in SonarQube configuration before running the interview:
     ```
     sonar.ai.codefix.enabled=false
     ```
   - Option B: Filter response when displaying:
     - Display `rule.htmlDesc` or `rule.mdDesc` (hand-written rule explanation) — **SAFE, identical across conditions**
     - Do NOT display `rule.codeFixComments` or related AI-generated fields if present — **UNSAFE, contaminates disclosure**

3. **What is safe to show**:
   - `rule.name`: Rule identifier (e.g., "Null pointer dereference")
   - `rule.htmlDesc` / `rule.mdDesc`: Hand-written explanation of why the rule matters
   - `rule.tags`: Rule categories (e.g., bug, vulnerability)
   - Code examples in the explanation (non-AI-generated reference examples)
   - **NOT** AI Code Fix suggestions or auto-generated remediation steps

### Rationale
- Hand-written rule explanations are **identical** across C1/C2/C3 (sourced from SonarQube's rule database, not from ranking algorithms)
- Showing them does **not** contaminate the ranking comparison (no treatment effect from explanation)
- They are **ecologically valid** — developers see these in real SonarQube UI when investigating alerts
- AI-generated suggestions are **not** available in real SonarQube alert investigation workflow for many enterprises with stricter governance policies
- Hiding AI suggestions preserves the validity of the disclosure and Part 3 evaluation

## Severity Vocabulary Display (Thesis Fix 1 Implementation)

### Design
All three conditions (C1, C2, C3) display severity using identical **3-level vocabulary** (HIGH, MEDIUM, LOW):

- **C1 (SonarQube native order)**: Display severity from `impact_severity` field
  - Source: SonarQube 10.x API impact model (direct from `/api/issues/search`)
  - Vocabulary: HIGH/MEDIUM/LOW
  
- **C2 (LLM with static features)**: Display severity from `llm_severity` field  
  - Source: LLM re-prioritization output (ranking_c2.csv)
  - Vocabulary: HIGH/MEDIUM/LOW (per system prompt updates)
  
- **C3 (LLM with full enrichment)**: Display severity from `llm_severity` field
  - Source: LLM re-prioritization output (ranking_c3.csv) 
  - Vocabulary: HIGH/MEDIUM/LOW (per system prompt updates)

### Why This Matters
Interview participants compare three lists side-by-side to evaluate "Which ranking is most actionable?" (RQ2) and "Which ranking do you trust?" (RQ3). If the severity labels differ between conditions (e.g., C1 shows HIGH/MEDIUM/LOW while C2 shows BLOCKER/HIGH/MEDIUM/LOW/INFO), participants perceive a difference that is an **artifact of vocabulary mismatch**, not a difference in ranking quality. This confounds the study results.

By using identical vocabulary across all conditions, differences in participant perception are attributable to the ranking algorithm, not label presentation.

## Rule Descriptions Caching

### Implementation
File: `results/{project_id}/rule_descriptions.json` (auto-generated by `sonarqube_extractor.py`)

Each entry:
```json
{
  "rule:S1135": {
    "rule_key": "rule:S1135",
    "rule_name": "TODO Tags Should Be Handled",
    "rule_description": "<p>When leaving a code object, explicit TODO comments should be used to...</p>",
    "rule_type": "CODE_SMELL",
    "rule_tags": ["cwe", "bad-practice"],
    "default_impacts": [
      {"softwareQuality": "MAINTAINABILITY", "severity": "LOW"}
    ]
  },
  ...
}
```

### UI Usage (Future Implementation)
- Load `rule_descriptions.json` once per interview session (cache in browser or server)
- When participant clicks "View rule explanation" on an alert, fetch matching rule from cache
- Display safe fields only (see "Critical: SonarQube AI CodeFix Suppression" section above)
- Do **not** make repeated API calls per participant — descriptions are identical across C1/C2/C3

## List-to-Condition Mapping

Conditions (c1/c2/c3) are rotated per project to prevent position-based bias:
- `c1_rank`, `c2_rank`, `c3_rank` columns exist in ranking CSVs
- Rotation is deterministic and documented in HTML comment in rendered template
- Neutral labels: Lists are shown as "List 1", "List 2", "List 3" to prevent priming

Example (in HTML source comment):
```html
<!-- C1=List 1, C2=List 3, C3=List 2 -->
```
